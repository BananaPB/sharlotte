# CLAUDE.md — [SHARLOTTE] project directives

This file is read automatically by Claude Code (and by all sub-agents defined in `.claude/agents/`) at the start of every session. It is authoritative on the project's conventions.

## 1. Project context

Before any task touching the business domain (ingredients, products, preparations, nutrition/allergen calculation), read `docs/vision.md` and `docs/domain-model.md`.

- SaaS developed solo, by a hobbyist developer (past experience: Symfony + React).
- Absolute priority: **readable, simple, and safe code** over "clever". When in doubt between an elegant-but-complex solution and a basic-but-clear one, choose the latter and explain why in a comment.
- Any non-trivial decision (architecture choice, added dependency, unusual pattern) must be **justified in one sentence** in the commit message or in the diff, so that human review stays possible without re-reading the entire Laravel/React documentation.

## 3. Strict rules (non-negotiable)

1. **Never an N+1 query**: any Eloquent relation loaded inside a loop must be eager-loaded (`with()`, `load()`). If in doubt, add `->withCount()` or check with Laravel Debugbar/Telescope locally rather than guessing.
2. **Never raw SQL without bindings**. Always Eloquent/Query Builder with bound parameters. If raw SQL is genuinely needed, it must be justified in a comment and go through `DB::raw()` only with static values, never a user-supplied value.
3. **CSRF**: never disable Laravel's CSRF protection. Inertia forms use the default middleware — do not add an exception without a documented reason.
4. **Validation**: all incoming controller-side data goes through a dedicated `FormRequest` (no inline validation in the controller beyond trivial cases).
5. **Authorization**: any action on a resource owned by a user goes through a Laravel Policy (`Gate`/`Policy`), never a manual check like `if ($user->id !== $resource->user_id)` scattered across controllers.
6. **Strict types**: `declare(strict_types=1);` at the top of every new PHP file. On the TypeScript side, no implicit or explicit `any` without a comment justifying why.
7. **Secrets**: never a hardcoded key, token, or credential in the code. Always `.env` + `config/*.php`.
8. **Migrations**: always reversible (a working `down()` method), never a destructive change to an existing column without a documented intermediate migration step.

## 4. Naming conventions

### Backend (Laravel/PHP)

- Controllers: `PascalCase` + `Controller` suffix (e.g. `InvoiceController`), one controller per resource, RESTful actions (`index`, `store`, `update`, `destroy`, etc.).
- Models: singular `PascalCase` (e.g. `Invoice`), relations named explicitly (`items()` rather than `getItems()`).
- FormRequests: `<Action><Model>Request` (e.g. `StoreInvoiceRequest`).
- Policies: `<Model>Policy`.
- Migrations: descriptive, timestamped name generated by Artisan, never rename a migration that has already been merged.
- Pest tests: one test file per class under test, `Test.php` suffix, describe blocks named in business language (`it('refuses to create an invoice without a client', ...)`).

### Frontend (React/TypeScript/Inertia)

- Components: `PascalCase`, one component per file, file named like the component.
- Inertia pages: in `resources/js/pages/`, mirroring the route structure (e.g. `resources/js/pages/invoices/Index.tsx`).
- shadcn/ui components: never modify the generated files in `resources/js/components/ui/` directly; compose on top of them in `resources/js/components/`.
- Custom hooks: `use<Name>.ts`, in `resources/js/hooks/`.
- Props typed explicitly via `interface` or `type`, never `React.FC` without typed props.

## 5. Laravel 13 / React 19 specific best practices

- Use implicit **route model binding** rather than manual `Model::findOrFail($id)` when possible.
- Prefer **Form Requests + Laravel Resources** (`JsonResource`) to format data sent to Inertia rather than serializing raw models.
- On the Inertia side, use `Inertia::render()` with **TS-typed props** (generate/maintain shared types if a generation tool is in place, otherwise document them in `resources/js/types/`).
- React 19: prefer **Server Actions/native forms** when relevant, otherwise Inertia's `useForm` for backend-bound forms.
- No `useEffect` to sync derivable state — compute it directly during render or with `useMemo`.
- Tailwind: no custom CSS unless truly impossible with utilities; respect the shadcn/ui theme tokens rather than hardcoded colors.

## 6. Rules for optimizing requests to Claude Code

- **One agent, one responsibility.** Don't ask the Dev agent to run linters or write tests: those are the roles of `quality` and `qa` (see `.claude/agents/`).
- **Minimal context.** Before reading a file, check whether it's already in the session's context. Don't re-read a file already seen without reason.
- **Targeted diffs.** Always work off a `git diff` or a list of modified files rather than rescanning the whole repo, except on an explicit request for a global audit.
- **No speculative exploration.** If a feature already exists in the Laravel starter kit (auth, profile management, etc.), reuse it rather than rebuilding it.

## 7. Commit & branch structure

- One branch per feature: `feature/<short-name>`, `fix/<short-name>`.
- Atomic commits, message formatted as `type(scope): description` (e.g. `feat(invoices): add PDF generation`).
- No `git push --force` on a shared branch. No direct merge to `main` without going through a PR.

## 8. Documentation to maintain

- `docs/architecture.md`: technical overview, updated by the Documentation agent after each structuring feature merge.
- `docs/changelog.md`: end-user-facing changelog (no technical jargon), updated on every merge.
- `docs/decisions.md`: decision log — what was chosen, what was rejected, and what it costs. Maintained by the CTO (`/cto`), never by the Documentation agent. Append-only: an existing entry is never rewritten, a changed decision gets a new entry superseding the old one. It is the counterpart to `architecture.md`, which describes the current state and _is_ rewritten.

## 9. Available sub-agents

See `.claude/agents/`: `dev`, `quality`, `qa`, `doc`. Invoked via the slash commands in `.claude/commands/` (`/feature`, `/audit`, `/test`, `/doc`) or directly by name for one-off needs.

`/cto` is deliberately **not** a sub-agent: it is a posture loaded into the main session, because an advisory conversation needs the context already in the session rather than a cold start. It decides and records in `docs/decisions.md`; it never writes application code.
